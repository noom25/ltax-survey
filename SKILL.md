# LTAX Survey Development Skill

## Purpose

Act as the project-aware development assistant for:

`https://github.com/noom25/ltax-survey`

This repository is the LTAX Offline PWA for Thai land/building tax field surveys. The normal data pipeline is:

**mobile field survey → local browser storage → `ltax_data_all.json` → `json_to_excel.py` / JSON bot → LTAX Online**

Do not treat this as a generic HTML project. Preserve the existing survey data model, chained workflow, offline behavior, photo linkage, and LTAX automation compatibility.

## When to Use

Use this skill when the user asks to:

- modify or add a survey form
- change the home page, SPA routing, search/view/edit/delete behavior
- change the chained Owner → Land → Land Usage → Building → Building Usage → Sign workflow
- change validation, required fields, auto-fill, or chain status badges
- change photo capture, grouping, matching, or IndexedDB behavior
- change JSON structure or `json_to_excel.py`
- change PWA build, service worker, manifest, or offline caching
- test the application with Selenium
- deploy the project to GitHub Pages
- troubleshoot mobile/iPhone/iPad/Android behavior
- connect the survey output to LTAX automation
- review or continue work documented in `PROJECT_STATUS.md`
- diagnose regressions in an existing flow

## Project Rules

### 1. Read project status first

Before making a non-trivial change, inspect:

- `PROJECT_STATUS.md`
- `README.md`
- the relevant `สรุปงาน_*.md`
- the actual source files involved

`PROJECT_STATUS.md` is the project's continuity document. Treat it as current project context, but verify important claims against source code.

### 2. Never edit generated `web/index.html` directly

`web/index.html` is generated by `build_pwa.py`.

When changing the application:

- edit `home.html` for the home/SPA layer
- edit the relevant `ฟอร์ม_*.html` source
- edit `ถ่ายรูป.html` for the photo page
- edit `admin_data.js` for province/district/subdistrict data
- then run:

```bash
python build_pwa.py
```

If the offline copy must also be updated:

```bash
python build_pwa.py --sync
```

Only modify generated `web/index.html` directly for emergency diagnosis, never as the permanent source change.

### 3. Enforce the mandatory survey chain (strict, blocking order)

The chain for Owner → Land → Land Usage → Building → Building Usage is **mandatory and blocking**, not a suggestion. A user must not be able to reach a later step while an earlier required step is missing.

```text
OWNER                      (required first — cannot be skipped)
  ↓
LAND                       (required before Land Usage or Building)
  ↓
LAND USAGE                 (required immediately after Land, before Building)
  ↓
BUILDING                   (required before Building Usage)
  — includes BOTH:
    • building on the owner's own surveyed land, and
    • building on land owned by someone else ("ปลูกในที่ดินคนอื่น")
    both cases must still pass through this same mandatory step and
    still require a completed Land + Land Usage record to attach to
  ↓
BUILDING USAGE              (required immediately after Building)
```

`SIGN / NO SIGN` is explicitly **excluded** from this strict enforcement. Sign keeps its existing, more flexible behavior exactly as it is today — do not add new gating/blocking logic to the sign step, and do not make sign availability depend on building/building-usage completion status unless that dependency already existed before this change.

**What "mandatory and blocking" means in practice:**

- Owner must exist before Land can be created for that owner.
- Land must exist before Land Usage can be created for that land.
- Land Usage must exist before Building can be created against that land — this applies even when the building sits on land belonging to a different owner; the "land owned by someone else" case is a data/ownership distinction, not an exemption from the gating sequence. The building record must still be linked back to a Land + Land Usage record (the record for the land it physically sits on, whoever owns it).
- Building must exist before Building Usage can be created for that building.
- The UI must not let the user jump ahead (e.g. hide/disable the "next" action, or redirect back to the missing prerequisite step) when a required prior step is incomplete.
- `chainState()` must be extended to detect and flag each of: owner missing, land missing, land usage missing, building missing (including the building-on-others'-land case), building usage missing — and to block progression accordingly, not just badge it as a warning.
- Existing/legacy records created before this enforcement may not satisfy the new gating; degrade gracefully (e.g. still allow viewing/editing legacy records) rather than hard-blocking valid historical data. Confirm the intended legacy behavior with the user before assuming.

The chain uses state such as `psnId`, `fullName`, `parcelCode`, `buildingCode` and `sessionStorage` (`ltax_next`).

When changing a form, check both:

1. standalone use
2. SPA/chained use

Do not break `window.__editQuery`, `window.__goHome()`, `window.openForm`, or the chain state.

### 4. Prevent "floating building" records

A building must remain linked to its land — this is now enforced by the mandatory chain in Rule 3, not just recommended. This applies identically whether the building is on the surveyed owner's own land or on land owned by someone else; either way it must be linked to a completed Land + Land Usage record before it can be created.

Important safeguards include:

- building `landAreaStr` is required where applicable
- land-use area calculations must use the correct key
- `autoFillLandArea()` should continue to populate land area when opened through the chain
- `chainState()` must detect incomplete land/building relationships and block progression, per Rule 3
- land-use remaining-area calculations must not silently consume the entire parcel when the building footprint is intended to be divided
- entry points that used to allow creating a Building without a prior Land Usage record (if any exist) must be closed off or redirected into the mandatory chain

When touching these areas, inspect the existing regression tests and the fix-flow documentation before changing behavior.

### 5. Preserve Thai administrative data

The project uses `admin_data.js` for complete Thai province/district/subdistrict data.

Do not hardcode a single province such as `33` into reusable forms.

When changing address fields:

- use `window.ADMIN_DATA`
- preserve province/district/subdistrict IDs
- preserve edit/load-back behavior
- verify all 77 provinces unless the change is intentionally scoped

### 6. Data persistence and offline rules

The application is designed for offline field work.

Important rules:

- Do not assume internet access.
- PWA service worker/cache must continue to work offline.
- Data is stored locally.
- Photo collections use IndexedDB to avoid the small localStorage quota.
- Photos embedded in survey records can still consume storage.
- Do not introduce network-only dependencies into core survey entry.
- On iOS/iPadOS, do not instruct users to simply open `index.html` via `file://`; use an HTTP server/app context as documented by the project.

### 7. Photos

The photo workflow supports:

- land/building/sign categories
- selecting a record code before capture
- remembering the last code
- quick capture into a waiting library
- multi-select matching
- grouping by time and GPS
- IndexedDB storage
- attaching matched photos to the combined JSON
- later extraction by `json_to_excel.py`

Do not change photo IDs or linkage semantics without checking how the JSON exporter and downstream bots consume them.

### 8. JSON is a first-class output

The main field export is:

`ltax_data_all.json`

The project has two downstream paths:

```text
ltax_data_all.json
        │
        ├── json_to_excel.py
        │       └── owner_land_building_template.xlsx + photos
        │
        └── bot_upload_json
                └── run_all_json.py
```

When changing JSON:

- inspect producers and consumers together
- maintain backward compatibility where practical
- handle old records when possible
- never change a field name casually
- verify nested usage records and photo data
- test with representative data, not only empty forms

### 9. Excel conversion

`json_to_excel.py` converts the combined JSON into the LTAX Excel workflow and extracts photos.

Before changing it:

- inspect the workbook template
- identify sheet names and column mappings
- verify owner/land/building/usage/sign relationships
- verify photo extraction
- run the conversion on sample data
- compare output against the expected LTAX template

### 10. LTAX bot integration

The survey project is part of a larger LTAX automation system.

There are two bot paths:

- legacy Excel path: `run_all.py`
- direct JSON path: `bot_upload_json/run_all_json.py`

Do not mix their assumptions.

For the Excel path, the project status notes that the intended command is:

```bash
python run_all.py --excel owner_land_building_template.xlsx
```

Do not silently rely on a different default workbook.

For direct JSON automation, keep the JSON loader, flattening logic, image extraction, common LTAX login/navigation helpers, and individual bot modules separated.

Login/OTP is interactive and must not be bypassed or hardcoded.

## Development Procedure

For a code change:

1. Identify the exact feature and its upstream/downstream dependencies.
2. Read `PROJECT_STATUS.md`.
3. Inspect the relevant source file(s).
4. Search for every function/key/state variable being changed.
5. Make the smallest coherent change.
6. Preserve existing interfaces and data keys.
7. Build the PWA if source files changed.
8. Run focused tests first.
9. Run broader regression tests when the change affects shared flow.
10. Inspect generated output and git diff.
11. Report exactly what changed and what was tested.

## Testing

Prefer existing Selenium tests where available.

At minimum, after UI/flow changes verify:

- page loads without JS errors
- all relevant forms open
- required validation works
- save works
- edit/load-back works
- search/view/edit/delete behavior still works when affected
- chained navigation still works
- local data survives reload
- photo linkage still works when affected
- PWA service worker still registers
- offline cache still opens the application when PWA behavior is affected

If a test suite exists in the user's environment, use it rather than inventing a replacement.

For browser driver problems, check the installed Chrome version and use a compatible driver mechanism such as `webdriver_manager` when appropriate.

## Deployment

GitHub Pages target:

`https://noom25.github.io/ltax-survey/`

Normal source-to-deploy flow:

```text
edit source
  ↓
python build_pwa.py
  ↓
inspect web/
  ↓
git add -A
  ↓
git commit
  ↓
git push origin main
```

If Git CLI is unavailable, the project has also used GitHub API deployment scripts. Do not assume a deployment script exists in the current checkout; inspect it first.

Remember:

- GitHub Pages has no local LAN server endpoint
- "ส่งข้อมูลไปคอมฯ" requires the computer/server mode
- field users can use "รวมข้อมูล (JSON)" and transfer the JSON back to the computer
- service-worker caching can make an old version appear after deployment; verify cache/version behavior before declaring deployment broken

## Mobile Rules

### iPhone/iPad

The project documents two practical modes:

1. PWA/HTTPS mode
2. local server mode such as Documents or a-Shell

For local field use, an HTTP origin is important for reliable browser storage behavior.

### Android

The project documents that Android can use the HTML directly in the supported field workflow, but do not generalize this to all browsers or future versions without testing.

## Coding Style

Prefer:

- small targeted changes
- existing function names and data conventions
- clear Thai UI text consistent with the current application
- defensive handling of old records
- no unnecessary frameworks
- no new build system unless explicitly requested

Avoid:

- rewriting the application into a framework without approval
- replacing localStorage/IndexedDB architecture casually
- changing JSON schema just to make code "cleaner"
- editing generated files as the permanent fix
- deleting working regression behavior
- adding online dependencies to the offline core
- changing LTAX field mappings without checking the downstream bot

## Troubleshooting Priorities

### Blank/broken PWA

Check:

1. generated `web/index.html`
2. `build_pwa.py`
3. escaped `</script>` handling
4. service worker cache/version
5. browser console errors

### Data disappears on iPhone/iPad

Check:

1. whether the page is running under a proper HTTP/HTTPS origin
2. whether the user opened the file directly with `file://`
3. localStorage/IndexedDB availability
4. whether the PWA service worker is active

### User can skip a mandatory chain step

Check:

1. whether the entry point into the next step (Land, Land Usage, Building, or Building Usage) checks for the required prior record before allowing navigation
2. `chainState()` logic for the missing-prerequisite case
3. `window.__goHome()` / `window.openForm` routing for a bypass path
4. whether the building being added is on land owned by someone else — confirm it is still routed through the same Land + Land Usage gate rather than a separate ungated path
5. confirm Sign was not accidentally gated by this change — it should remain on its prior, unblocked flow

### Building is not linked to land

Check:

1. `landAreaStr`
2. `autoFillLandArea()`
3. land-use area keys
4. `chainState()`
5. `ltax_next`
6. edit/load-back relationships

### Dropdown data is wrong

Check:

1. `admin_data.js`
2. province/district/subdistrict IDs
3. dynamic loading code
4. edit/load-back code
5. whether the form still contains hardcoded administrative values

### Export is wrong

Trace the complete chain:

```text
form data
→ local storage
→ ltax_data_all.json
→ json_to_excel.py OR bot_upload_json
→ downstream mapping
```

Never fix only the final output without checking the producer.
